Pay with Clear, on any website.

A script any shop can paste in, or ask their AI to add, that turns their own button into Pay with Clear, with card always one tap away. Clicking it opens Clear’s modal on their page: members approve, new customers can join, and anyone can pay by card. It is the counter’s payment, online: the same order, the same approval on the member’s phone, the same points. Drawn on Mi Casa Tacos’ catering checkout.

The decisions

  • Their button, Clear’s modal. The script attaches to any element the shop already has. Clear never draws the trigger, so it fits any design, and an AI can wire it up in one step.
  • The amount never comes from the browser. Either a price made in the merchant app (no server needed) or a payment the shop’s server creates with its secret key. A page can’t be edited into charging $0.01.
  • Clear first, card always there. Cards run on the shop’s own Stripe account, connected in the merchant app as for the counter; Clear never processes a card itself. Clear’s card fee is the counter’s (30¢ a sale on pay-as-you-go, none under $10), taken by Stripe as the platform fee. A shop with no card processor connected gets Clear only. An unfinished sign-up never costs the shop the sale.
  • The modal is Clear’s page. An iframe from pay.useclear.org, so the shop’s site can’t read a phone number, code or identity detail typed into it. Shops can set the accent and their logo; the rest always looks like Clear, so a fake is easier to spot.
  • Pay with Clear connects the account, then pays. The shop’s button says Pay with Clear. Members connect by approving in the Clear app (the request goes to their phone, or the app opens on the phone they’re using) or by signing in with email or phone in the modal. A QR code is never shown on a phone.
  • Light sign-up in the modal, the heavy checks outside it. Name, birth date and address in the modal; the ID photo and bank link continue in a new window (or on the phone, from a computer), because they need a camera and the bank’s own sign-in, and some vendors won’t run inside another site’s frame.
  • One payment object, counter or online. An online payment is an order with a Clear or card tender. It shows in the merchant app’s Charges beside counter sales, marked Online with the website or link, refunds the same way, earns rewards points, and reaches the member as the same approval. Card money reaches the shop in its Stripe payouts; Clear money in its Clear payouts, as today.
  • The public API is versioned and only grows. Its types live apart from the merchant app’s, every request names a version, and nothing published is changed or removed without a new one.
  • Written for AI as much as for people. An llms.txt, a paste-in prompt, and an MCP server, so “add Pay with Clear to my site” works in whatever tool the shop uses.

1 · The snippet

Two ways in, both a few lines. With no server, the button names a price from the merchant app. With a server, the shop creates the payment with its secret key and hands the button its id. Either way the page gets onSuccess, and the server gets a signed webhook, which is the one to trust for fulfilment.

With a server

Node; the amount stays server-side
js
// server
import Clear from "@useclear/node";
const clear = new Clear(process.env.CLEAR_SECRET_KEY);

const payment = await clear.payments.create({
  amount: 18532,            // cents
  currency: "usd",
  reference: "catering-1042",
  lines: [{ name: "Taco tray for 12", amount: 14900 },
          { name: "Agua fresca, gallon", amount: 1100, quantity: 2 }],
}, { idempotencyKey: "catering-1042" });

// page
Clear("pk_live_mc8Q2v").attach("#pay", { payment: payment.clientSecret });

The webhook

Fulfil on this, not on the page
js
app.post("/clear/webhook", express.raw({ type: "*/*" }), (req, res) => {
  const event = clear.webhooks.verify(req.body, req.headers["clear-signature"]);
  if (event.type === "payment.succeeded") markPaid(event.data.reference);
  res.sendStatus(200);
});

What the shop can set: accent, logo, locale, methods (["clear", "card"] or one of them) and email to prefill. What it can’t: the amount, the modal’s layout, or anything typed into it.

8 · Behind the screens

A public, versioned API over the order and approval machinery that already exists. Merchant routes stay as they are; the public API is a separate surface with its own keys, versions and contracts.

Keys and versions

Publishable keys (browser, can only start a modal for an allowed site) and secret keys (server). Test and live are separate. Every request carries Clear-Version: 2026-10-16; changes only add fields or a new version.

packages/public-api-contracts

Payments

A payment wraps an order: lines, amount, reference, methods allowed, and its status (requires_customer, processing, succeeded, failed, canceled). Creating one is idempotent by key. A Clear tender goes through the existing member approval; a card tender uses the shop’s connected Stripe account.

POST /v1/payments, GET /v1/payments/:id, POST /v1/payments/:id/cancel

Prices and links

Prices are the merchant app’s Inventory items. A link is a stored payment template with a slug, expiry and the over-time switch.

GET /v1/prices, POST /v1/payment_links

Refunds

The existing refund path; Clear refunds return to the member’s balance or reduce the plan, card refunds go through Stripe.

POST /v1/refunds

Webhooks

Signed, retried with backoff for 3 days, logged per delivery. Events: payment.succeeded, payment.failed, payment.canceled, refund.succeeded.

POST /v1/webhook_endpoints

The modal

apps/pay at pay.useclear.org, framed only by allowed sites (frame-ancestors from the shop’s list). Talks to the page by postMessage, checked by origin. Sign-in by an approval request to the Clear app, or a code by text or email; on a phone, a deep link that opens the Clear app and returns; the join steps that leave the frame hand back by a short-lived session.

apps/pay, packages/clear-js

Stripe checkout, later

For shops already on Stripe’s checkout: Clear as a custom payment method in Stripe’s Payment Element and Express Checkout, set up on the shop’s connected account. Stripe shows it; Clear processes it. Not in Payment Links.

Stripe custom payment methods

9 · Where the code lives

In the monorepo, published under @useclear. Everything shares the API, the order types and the approval flow, so one change updates all of it. Claim the npm scope @useclear now: nothing is published under it today. Don’t use the name Clearpay anywhere: it is Afterpay’s brand in the UK.

tree
apps/
  api/                      public /v1 routes beside the existing merchant routes
  pay/                      the modal and payment-link pages · pay.useclear.org
packages/
  public-api-contracts/     versioned public types · never edited in place
  clear-js/                 the browser script · js.useclear.org/v1 and npm @useclear/js
  clear-node/               the server SDK · npm @useclear/node
woocommerce plugin          its own repo, later (PHP, WordPress's own SVN releases)

Order

  • 1. Payment links. No code from anyone; reuses the phone pay page.
  • 2. The script, the modal, the Node SDK and webhooks. Clear first.
  • 3. Card in the modal on the shop’s own Stripe.
  • 4. Docs for AI and the MCP server.
  • 5. Later: Stripe custom payment method, WooCommerce, phone-app SDKs, Shopify (an approved-partner application).

Open

  • Paying over time online reaches buyers in any state. Counsel should confirm the structure (the shop originates, Clear buys) before split checkout goes live online.
  • Monthly payouts meet online shops used to about two days with Stripe. Decide what online merchants are offered before the pitch.
  • Pay first, finish joining later: whether a new customer can pay over time before identity and bank checks finish, and with what limit.
