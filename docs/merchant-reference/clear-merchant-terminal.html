Clear Terminal: devices, tables and the Point.

What the counter hardware changes in the merchant app, the pages a customer’s phone opens from a Point, and the member app. Drawn on a restaurant, Mi Casa Tacos, because tables, menus and order numbers don’t happen at a tire shop. Hardware, prices and drawings live on the Clear Terminal and Clear Point pages; this file is the software.

The decisions

  • Every new thing is a device, and devices live in one pane. Settings › Devices grows from readers and this tablet to Points, the drawer and printers. Adding any of them is one action, so it is one sheet that asks what you are adding.
  • The tablet talks to the drawer, printer and reader directly. Only the Point listens to the server. A cash sale opens the drawer and prints with the internet down. The Point catches up when the connection comes back. This is the one rule the backend and the app must both keep.
  • Nothing here changes how money moves. Cash is still a cash tender; a Point payment is still a Clear or card tender on an order. The Point adds where a bill is shown and who opened the drawer, never a new kind of payment.
  • Tables is a page only for shops that serve at tables. Off by default; Settings › Counter turns it on. A counter-service shop never sees it, so the nav stays six items for them.
  • A table rests on its number; a seated party gets their table’s Point. Free, a table Point shows its number large with the menu code. Seating a party inverts it with their first name until they order, so they find the table and read the menu before anyone comes over.
  • One code per Point, and the phone page follows the Point. useclear.org/p/A7K2 opens the menu when the table is free, the bill when one is sent, the receipt once paid. Nothing to print, nothing to update.
  • Suggestions and One more round are drawn but switched off. They need ordering from the phone, which is later work. Their switches show "Coming later" rather than being hidden, so the pane doesn’t change shape when they arrive.
  • The drawer logs every open. With a sale it is the sale; without one it is a No sale with a PIN and a reason. Close the day shows the count, so an owner can see who opens it.

The drawer’s pane is its rules. It opens on a cash sale, always. A No sale needs a PIN and a reason; who may do one is the owner’s choice. Drawers cabled to a receipt printer work too: the switch tells the app to send the printer’s drawer pulse instead. Printers say what prints by itself, and show the labels at size.

13b · The Pay case

Owner · Table 12 in a Pay case

An optional case puts a Stripe M2 under a Point’s screen and adds two stainless buttons, Call and Bill. The Point detects the case through its pogo pins; the reader is linked to the Point once, in its pane. The tablet can hold one reader connection at a time (Stripe’s SDK), so it connects to a table’s reader when that table’s bill is sent to its Point, and lets go when the payment is done. A second card payment at the same moment waits, or goes to another device running the app.

14 · Behind the screens

What the API and database need, by area. Names follow the existing routes and the contracts package; the prompt alongside this file turns each into a phase.

Devices

One devices table with a kind (point, drawer, printer) and per-kind settings; readers stay where they are. Claim a Point by its code; pair a drawer by its Bluetooth ID; store a printer’s address and language.

GET/POST /api/merchant/devices, PATCH /:id, POST /api/merchant/points/claim

Points

Points report whether a Pay case is fitted and send its button presses (Call, Bill); a Point can be linked to the M2 inside its case. Each Point has a state the server owns: idle mode (number, menu, showcase or pay), held for a party, the order or alert it is showing, battery and last seen. Points authenticate with a per-device key set at claim. Plugged-in Points hold a stream; battery Points ask on wake.

GET /api/device/point/state (device key, ETag), GET /api/device/point/stream (SSE), POST /api/merchant/points/:id/show

The phone page

Public, no sign-in. Resolves a code to what the Point shows now: menu, bill, receipt or wait list. Pay creates the same Clear or card tender the counter would, on the shop’s Stripe account.

GET /api/p/:code, POST /api/p/:code/pay, GET /api/r/:receiptCode

Drawer

Drawer events join the drawer session: opened for a sale, a refund, a No sale (reason, who approved), or by key; and shut. Events carry the tablet’s own ID and time, so ones made offline sync once without doubling.

POST /api/merchant/drawer/events (idempotent), GET /api/merchant/drawers/:id/key

Tables and the wait list

Tables belong to the shop, with seats; an open order can belong to a table (its tab). A table can be held for a party (name shown or Reserved, seated at, clears on first item, staff, or 15 minutes). Wait-list parties, their place and their text. Table ready and order ready are alerts sent to a Point and, if there is a number, by text.

/api/merchant/tables, /api/merchant/waitlist, POST /api/merchant/alerts

Printing

Nothing on the server: the app draws each label at the printer’s resolution and sends it in the printer’s language. The server only stores which printer prints what.

Settings on devices; the order’s receipt route already exists

Menu

Inventory items get On the menu and categories get an order. The phone menu and the showcase read the same list.

GET /api/p/:code/menu

Open

  • Point firmware is its own repo. This file fixes the device API it talks to; the firmware follows it.
  • Ordering from the phone (suggestions, One more round, ordering from the menu) waits for a decision on how orders reach the kitchen. Its switches are drawn off.
  • Square readers come with the card-connector layer, not this work.
  • Texts use the Twilio route receipts already use. Wait-list texts need the shop’s consent line on the join page.
